# Feature associations in generated scalar readers

When a native part contains named scalar records, the generated reader can compare those records with the named dimension declarations in its configuration. It uses the saved display unit for lengths and degrees for angular declarations, and requires agreement within the reader's numeric tolerance. It separately finds feature markers that match both the declared name and the native feature ID. If several features share a declaration, a preceding marker offers a hypothesis. The evidence retains all matching candidate IDs.

Run `kit run --root . auto --input part.SLDPRT --directory /tmp/part-run`. The member entries in `Input-scalar-streams.json` include the raw values, per-record candidates, marker offset and status. After applying `NamedScalarReader.patch`, use the generated script with `--member Contents/Config-0-ResolvedFeatures --owners` to obtain the same result directly from a part. Bare streams have no configuration declarations for this comparison.

The P05 edited revolution file produced four associations: three to AnnulusProfile and one to Revolution. Each feature name, parameter name and numeric value matched the hashed native reopen measurement. This comparison does not measure an absolute byte offset through the vendor API. On the turbine wheel, 33 of 132 records had one matching declaration and an agreeing marker, 11 had multiple matching declarations with a marker candidate, eight had only a unique declaration, one remained ambiguous and 79 had no matching declaration. No native owner measurements were found for that wheel. The classifier leaves count semantics, rounded display values outside the tolerance and configurations with repeated feature IDs unresolved.
