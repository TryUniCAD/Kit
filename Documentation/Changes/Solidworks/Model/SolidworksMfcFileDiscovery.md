# Read-only MFC file discovery

The research tool [InspectMfcFiles.py](../../../../re/tooling/sw2026/InspectMfcFiles.py) inventories on-disk `mfc140u.dll` candidates without loading them. This supports resolving the actual x64 MFC count implementations imported by the pinned `swccu.dll`, whose selected imports use ordinals `12087` and `14278`. An ARM64 or hybrid on-disk image and its raw export table do not establish the implementation used by x64 emulation. This tool supplies file identities for a later binding decision; it does not make that decision or promote the count grammar.

Run the committed script with the guest's absolute Python executable, `-B`, and an absolute `--output` path naming a new external task-owned directory with an existing parent. The oracle owner runs that metadata-only command from macOS through `prlctl exec --current-user "Windows 11"`. The worker preparing this change must not execute it or access the VM. No SOLIDWORKS application is launched or attached to by the script.

`--solidworks-root PATH` may be repeated for explicit installation directories. Otherwise the tool selects `SOLIDWORKS Corp\SOLIDWORKS` beneath the first available `ProgramW6432`/`ProgramFiles` identity. An existing SOLIDWORKS root requires a regular `SLDWORKS.exe` witness. The executable is opened read-only for its complete size/SHA-256, raw PE machine and version-resource metadata, and is never run or loaded. Recursive searches are limited to those installation roots, `%SystemRoot%\WinSxS`, and `Common Files\Microsoft Shared` and `Microsoft Visual Studio` beneath the available Program Files identities. Two additional exact shared-runtime paths, `%SystemRoot%\System32\mfc140u.dll` and `%SystemRoot%\SysWOW64\mfc140u.dll`, are probed without enumerating those directories. No drive-wide, registry, process, module-memory, service or licensing search occurs.

Only candidate DLL files whose name equals `mfc140u.dll`, case-insensitively, and the exact executable witness beneath each explicit SOLIDWORKS root are opened. The script also hashes its own source for provenance. Directory metadata is enumerated; other file contents, including license files, are not read. Reparse points and symlinks are rejected or skipped and recorded. Licensed input beneath a repository checkout is rejected. Output must be outside repository checkouts, Windows and installation roots, and must not exist before launch. The tool never copies a DLL or executable, emits code bytes or writes into a vendor directory. It imports only Python's standard library and disables bytecode-cache writing.

Each found file records its complete size and SHA-256, exact integer file identity and modification time, COFF machine and optional-header magic, and export-directory identity. Metadata for the two selected ordinals includes the ordinal base/index, aliases, RVA, file offset and section, or an explicit missing/unassigned/forwarded result. PE reads are bounded to file-backed ranges. A changed file or invalid metadata is reported as an error. The raw COFF-machine value and `machine_is_amd64` comparison describe disk headers only. They do not prove a hybrid view, mapped-module identity, executable instruction set, primitive width or correct import binding. No function bytes or full export listing are published.

Both candidate DLLs and executable witnesses receive bounded PE `RT_VERSION` decoding. The parser follows only the numeric version-resource type, checks directory/data bounds and tree depth/cycles, verifies `VS_VERSION_INFO` framing and the fixed-info signature, and records all thirteen documented `VS_FIXEDFILEINFO` DWORD values. Each language entry carries the resource length/hash and its observed file/product version words. Dotted and four-digit-build strings are computed presentations of those words, not claims that a `StringFileInfo` text value was decoded. Other resource types and child text tables are not interpreted or dumped. Missing resources remain absent; malformed or unsupported framing is reported without supplying the expected version as an observation.

Each installation root's `executable_witness` records the expected executable SHA-256 `3f6844591c7456a476bdc141817a21c3c10f770e12347a698eef5ea8ad60d1fe` and expected file-version words `[34, 5, 2, 604]`, displayed as `34.5.2.0604`, separately from its observed metadata. `sha256_matches_expected` compares actual bytes. `observed_file_version_matches_expected` is null when no version resource was decoded and otherwise compares every decoded language entry. `verified_pinned_executable` requires both the digest match and an observed version match without a metadata error. A mismatch remains explicit identity evidence and does not turn filesystem enumeration into application or count-grammar acceptance. Witnesses are nested under their installation roots and do not inflate the candidate DLL count.

The new directory contains progressive `Record.json` and terminal `Inventory.json`. They preserve the guest interpreter and script argument arrays, Python executable/version identity, tool SHA-256, timestamps, roots, exact-file probes, skipped paths and errors. The host transport command remains the oracle owner's separate provenance. Optional `--source-revision` records an operator-supplied full commit identity; the script does not run Git to verify it. `scan_complete` is false when errors or skipped reparse paths leave an enumeration gap. Missing installation/runtime directories are recorded as absent. Exit `0` means the bounded inventory completed without such gaps, including a possible zero-file result; exit `2` reports a partial inventory. Neither exit proves an x64 implementation was found. `native_implementation_bound` and `acceptance` remain false in every report.

The [research artifact policy](../../../Reference/Research/ResearchArtifacts.md) keeps all licensed DLLs outside repository checkouts and prohibits distributing them. Publish only reviewed, appropriately redacted metadata when evidence is ready; private paths and command arguments in the raw external report are not automatically public evidence. If filesystem discovery finds only ARM64/hybrid candidates, the oracle owner separately decides whether mapped-module inspection is needed. This tool performs no retries, recovery, process operations, COM calls, injections or native execution.

Initial worker verification was AST parsing and static source/link/format review only. The worker did not execute the script, a codec, a schema, tests or a guest command.
