# A DbgEng attach request can return before the initial stop

An AMD64 DbgEng observer on Windows ARM64 first tried to set detach-on-exit before requesting attachment. `AddProcessOptions` returned `0x8000ffff`. A second attempt requested attachment to the owned SOLIDWORKS process and waited for the initial stop before setting process options. The attach request succeeded, and the initial stop remained unobserved during the bounded wait. `DetachProcesses` succeeded and Windows reported debugger absence on the same process handle. The pristine controls saved and reopened in both attempts. [Native setup receipt](../../../../../re/solidworks/measurements/2026/DrawingBlankSaveAggregateSetupNative01.json) · [AttachProcess](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/dbgeng/nf-dbgeng-idebugclient-attachprocess)

Read the engine options before attach. If `DEBUG_ENGOPT_INITIAL_BREAK` is clear, enable it and verify the option before making the attach request. This obtained a verified initial stop on the exact owned process in the third control trial. Set process options and arm the execution breakpoint after that stop. [DbgEng engine options](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debug-engopt-xxx) · [Native control receipt](../../../../../re/solidworks/measurements/2026/DrawingBlankSaveAggregateControlNative01.json)

The third trial armed the processor breakpoint and received no stop sample. The observed native control and both pristine brackets saved and reopened cleanly. Explicit breakpoint removal returned `0x8000ffff`. Detach succeeded and debugger absence was verified on the same owned process handle. The observer used one message for either timeout or cancellation after the save. Its record leaves the exit reason unresolved. Log those exits separately in a repeat. Require the control to produce the expected four-byte sample and save and reopen cleanly before tracing the generated drawing.
