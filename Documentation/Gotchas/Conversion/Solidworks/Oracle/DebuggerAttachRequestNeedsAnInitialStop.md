# A DbgEng attach request can return before the initial stop

An AMD64 DbgEng observer on Windows ARM64 first tried to set detach-on-exit before requesting attachment. `AddProcessOptions` returned `0x8000ffff`. A second attempt requested attachment to the owned SOLIDWORKS process and waited for the initial stop before setting process options. The attach request succeeded, and the initial stop remained unobserved during the bounded wait. `DetachProcesses` succeeded and Windows reported debugger absence on the same process handle. The pristine controls saved and reopened in both attempts. [Native setup receipt](../../../../../re/solidworks/measurements/2026/DrawingBlankSaveAggregateSetupNative01.json) · [AttachProcess](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/dbgeng/nf-dbgeng-idebugclient-attachprocess)

Require an initial stop on the exact owned process before setting its process options or arming an execution breakpoint. The retry stopped during debugger setup, so debugger startup behavior and AMD64 emulation support remain open. Both attempts ended before the hardware breakpoint was armed. The generated drawing save branch remains unmeasured. [Drawing save branch map](../../../../../re/solidworks/records/DrawingSavePostEventBranches2026.md)

In a later owned control trial, read the engine options before attach. If `DEBUG_ENGOPT_INITIAL_BREAK` is clear, enable it and verify the option before making the same attach request. It asks the engine to stop at the initial event. Require the reduced native control to reach the hardware stop and then save and reopen cleanly before tracing the generated drawing.
