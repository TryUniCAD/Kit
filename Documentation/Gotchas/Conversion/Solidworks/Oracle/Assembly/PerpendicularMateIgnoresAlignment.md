# The ordinary perpendicular command ignores explicit alignment

An aligned coincident or parallel writer uses internal alignment `1` after the API's `0` selection is translated. It is tempting to reuse that value when adding a perpendicular class with the same two-geometry archive tail.

The pinned 2026 perpendicular command takes a different path. The API enum `2` branch at `sldasmu.dll 0x3f989b74` supplies zero to the shared command constructor at `0x3f989b90`, before the call at `0x3f989b99`. Coincident and parallel pass the translated alignment register. The common runner applies the model alignment setter only for internal `1` or `2`. The perpendicular construction edge therefore does not apply that explicit alignment setting.

Preserve the ordinary constructor state until the actual perpendicular setter/solve path proves otherwise. Record the COM alignment separately and require its observed persistence; do not infer its numeric API result from a saved parallel graph. The shared serializer is evidence for framing, not all runtime behavior: eleven bounded primary virtual cells differ between perpendicular and parallel.
