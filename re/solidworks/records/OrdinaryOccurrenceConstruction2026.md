# Ordinary external part occurrences in SOLIDWORKS 2026

This record covers the ordinary, resolved, nonvirtual part occurrence in a single-configuration assembly. The native implementation is from SOLIDWORKS 2026 SP05.2, `sldworks.exe` build `34.5.2.0604`. Addresses are preferred virtual addresses in `sldmodu.dll`, SHA-256 `569a081928ad24afac5408cc15a1034d18e89b2c5001428a64115a3cc497067e`, unless another DLL is named. The disclosed A12 empty, A13 single-part and A14 repeated-part assemblies are identified by the [source manifest](../v2026/corpus/assembly-synchronized/Manifest.json). A15 and A16 remained sealed while deriving these rules.

## Configuration registration and shared file identity

Ordinary `onAddReference` calls the one-reference registration helper at `0x4b6abb30`. The helper roots the path in the actual containing model at `0x4b8d4983`, appends the reference at `0x4b8d4990`, and calls `getOrAddObject` at `0x4b8d4ab1`. Lookup `0x4b8bfac0` partitions by chain length, hashes at `0x4b8bfb78`, and verifies chain equality at `0x4b8bfba0`. A new root entry reaches the configuration's `+0x1f90` slot at `0x4b8d1a0c`. Its implementation `0x4b8c9450` appends to `fce8` at `0x4b8c947b`. The modern loader also appends in archive order at `0x4b8c087a`.

A configuration can register several missing paths during activation. On `moConfiguration_c`, slot `+0x1ca8` targets `0x4b8c7a80`, reached from `moConfigObject_c::activateModel` at `0x4b8a80fb`. The activation branch at `0x4b8c80c8` calls helper `0x4b8d1db0`, whose ordinary model path calls `moConcept_c::getFeatures` at `0x4b8d1e3a`. The unfiltered direct-list branch of `getFeatures` copies `f60` head-to-tail into its feature array at `0x4bdab778`–`0x4bdab7c1`. Activation starts at the last index at `0x4b8d1e50`, filters reference features at `0x4b8d1e7f` and registers each at `0x4b8d1f4a`. The next iteration decrements the index at `0x4b8d20b4`. The composer follows this activation path by constructing all ordinary occurrences before their configuration rows. A14's registration order agrees with this path. Its individual runtime call sequence was not instrumented. [Configuration order gotcha](../../../Documentation/Gotchas/Conversion/Solidworks/Archive/ExternalReferences/ConfigurationOccurrencesFollowRegistrationOrder.md)

Two references to the same generated child share a directory record. `sldarchiveu!0x319ff850` increments the record's active-use count for an ordinary directory connection. Each occurrence owns its own external feature and the backlink names that occurrence. Each configuration row owns its options copy, contextual component, path, path list, path leaf and containing-file wrapper. The wrapper is allocated separately at `0x4be8bdd5`. The embedded file definitions use the containing assembly's shared path and name handles. `moSharedFileDef_c::Serialize` obtains those handles through `moCStringMgr_c::getStringHandlePtr` at `sldarchiveu!0x319fe9aa` and `0x319fea2c`. The A14 CMgr leaf and wrapper definitions all alias archive slots 24 and 25 for path and name, respectively. The corresponding Config-0 definitions pool those identities in their own object map.

## Generated ordinary occurrence process

The research constructor accepts the generated child part's self-file record, active configuration and configuration manager header. It creates one child directory entry from that identity, places it after the parent self entry, then links each Config-0 occurrence directly to slot 4. Directory `f60` comes from the child's self-file save event and `f70` from its configuration manager save event. The directory owns the occurrence count. Its configuration selector is absent. Each occurrence owns the actual child configuration selector. Generated child documents without an explicit display-state entry retain the selected insertion options' display state.

The process derives the child's bounding box from the generated polygon's actual sketch coordinates and blind depth. The stored rigid transform uses the child's basis vectors in parent coordinates as rows and its origin in parent coordinates as translation. A placed box transforms the child's sphere center and all eight corners and preserves the radius. Each parent cache uses the same sequence of resolved, visible, ordinary occurrences for this profile. `calcBBox` calls the bounds traversal at `0x4b689878`, assigns its regular accumulator to `f1a18` at `0x4b689896` and assigns the second accumulator to `f1a20` at `0x4b689a16` when requested. The bounds handler transforms the admitted child box at `0x4b6ca447` and unions it at `0x4b6ca455`.

The insertion path and the bounds handler both call `mgBBox_c::operator|=` (`sldmgu!0x31ddfff0`). It takes the componentwise low minima and high maxima. For current sphere `(c,r)` and incoming sphere `(q,s)`, it computes `d = |q-c|` and `m = (r+s+d)/2`. If `m <= r`, the current sphere encloses the incoming one. If `m <= s`, it assigns the incoming sphere. Otherwise it writes center `c + (q-c)*((m-r)/d)` and radius `m`. The helper at `sldmgu!0x31dea0c0` then measures squared distance `t` to the farthest corner of the union's box. It replaces the shifted sphere with the point-pair box sphere if `t + 5e-9 < m*m` or if `m > 1e-10` and `t * 1.000000005 < m*m`. The thresholds come from this build's constants at `0x31f45618`, `0x31f447f8` and `0x31f45640`. The composer folds these unions in occurrence insertion order and uses the default sphere mode. A14's two native caches match all ten computed doubles when the rule is applied to its disclosed local bounds and placements. [Sphere merge gotcha](../../../Documentation/Gotchas/Conversion/Solidworks/Archive/ExternalReferences/AssemblyOccurrenceBoundsMergeSpheres.md)

The [guarded single-occurrence test](../../../tests/Convert/Solidworks/Research/Assembly/OccurrenceBundleTests.py) generates identity and rotated, translated placements. The [repeated-occurrence test](../../../tests/Convert/Solidworks/Research/Assembly/RepeatedOccurrenceBundleTests.py) generates three placements from the same polygon part and checks both accumulation branches, separated feature order, configuration registration order, distinct context records and shared handles. Config-0, CMgr, ResolvedFeatures, mates and headers round-trip through the guarded process with no runtime input reads. The existing empty and single-occurrence container hashes are unchanged. Repeated-assembly native acceptance and other component states remain pending.

## Initial native measurement and derivative stamps

The controlled identity-placement measurement opened the generated assembly with errors and warnings both zero, resolved its single independently generated child, and rebuilt with the expected body and mass properties. The native save to a separate file succeeded. A fresh process reopened the derivative with warning 32, and its rebuild restored the same geometry. The child's disk hash remained unchanged through both phases. The passing controls and generated artifact hashes are in the [native measurement](../measurements/2026/GeneratedSingleOccurrenceNative01.json).

An independent archive projection matched the generated reference's `(f3e0, f3e8, f3f4)` of `(101, 1794700000, 101)` to the unchanged child's header `f40`, header `f48`, and model `f1300`. The vendor derivative wrote `(132, 1794894176, 102)` for those same occurrence fields. Its directory `f60` and `f70` remained `1794700051` and matched the child's self-file and configuration-manager save events. Both files resolved the child directory at direct slot 4 with the same child configuration and the same occurrence identifier and ordinal. [Hash-bound archive projection](../measurements/2026/GeneratedOccurrenceDerivativeStamps01.json)

A native stale-reference helper explains the geometry-stamp mismatch. `moReference_c::isGeometryOutOfDate` calls `0x4bbc4740` at `0x4bbc6feb`. For a part, virtual slot `+0x19e0` selects `getGeometryChangeStamp` at `0x4b5602e0`, which reads `f1300`. Its `+0x1490` predicate returns zero. When the helper reads an occurrence `f3f4` greater than the child's geometry stamp, it returns stale immediately if the child reports the constructor stamp 101 (`0x4bbc487a`–`0x4bbc489c`). The derivative's persisted pair `102` and `101` meets that condition if evaluated before child regeneration. This identifies a native stale branch without establishing which check sets the public open warning.

A [prior paired native child-save probe](AssemblyRebuildDecision2026.md#paired-child-save-intervention) established that saving a rebuilt child can remove this class of derivative reopen warning. The generated bundle comparison independently identifies the same divergence in persisted child update state. It leaves the exact warning branch and the effects of saved-copy identity and additional native metadata open. The rotated placement, synchronized derivative reopen, dimension edit, and held-out acceptance still need controlled native measurements.
