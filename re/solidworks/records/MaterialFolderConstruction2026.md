# Material-folder construction in SOLIDWORKS 2026

Full CAD success criteria remain unmet. The research factory now emits the native current-store flag encoding for a fresh empty material folder. Remote CI and controlled native measurements of the changed generated bytes remain pending. The title-regeneration caller remains untraced.

## Scope and field classification

The English empty-material caption is declared resource vocabulary, `Material <not specified>`, selected by string ID `0x4497`. It is not inferred from the three saved copies. The concrete `moMaterialFolder_c` constructor loads that resource and calls the inherited feature-name setter. A separate native material-folder operation can replace an empty incoming title with that resource and rename the actual folder.

There are distinct owners:

| Field or operation                              | Meaning and classification                                                                                                                                                                          |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Inherited `moNode_c.f18 -> moNodeName_c.f08`    | Persisted node-name text. An arbitrary incoming name is authored presentation input, but native material-title operations can overwrite it with a derived title. It is not an unserialized UI cache |
| Material folder `f378`                          | Separately serialized material string at runtime `+0x378`; constructor initializes an empty CString. It is not the inherited node name                                                              |
| Runtime material-folder `+0x380/+0x384`         | Separate material-related Boolean states, packed together by the material serializer; neither is the title string                                                                                   |
| Title selected for the empty-material operation | Derived from the concrete class, empty incoming title and active localized resource, under the native operation's branch conditions                                                                 |

The measured `authored material` input remains valid evidence of caller-authored data, not donor content. Its loss in all three saved-copy reopenings prevents a claim that arbitrary material-folder names survive that workflow. The observation does not justify classifying every system-folder name as derived, or replacing incoming names indiscriminately.

## Concrete receiver and name getter/setter

Constructor `0x4beae310` first invokes folder base `0x4beae110`, then installs primary material-folder vtable `0x4d04c1f8` at `0x4beae32a` and secondary table `0x4d04dee8` at runtime `+0x90`.

The actual primary dispatch is:

| Slot      | Target       | Recovered role                                                                     |
| --------- | ------------ | ---------------------------------------------------------------------------------- |
| `+0x88`   | `0x4bb4d460` | Inherited `moFeature_c::name`                                                      |
| `+0x90`   | `0x4bb3c560` | Inherited `moFeature_c::changeName`                                                |
| `+0x11b8` | `0x4beb1f10` | Material-folder `SerializePass2` override                                          |
| `+0x1568` | `0x4beb6b20` | Returns base-name resource ID `0xa1e2`                                             |
| `+0x18e8` | `0x4beb5800` | Compares the inherited name against resource `0x4497`; returns whether they differ |
| `+0x1ce0` | `0x4beb3fd0` | Material-folder owner/title operation, including empty-title fallback and rename   |

`moFeature_c::name` calls `moNode_c::name` at `0x4c03e5c0`. That leaf reads runtime node `+0x18` and returns the CString at the name object's `+0x08`, or a shared empty CString for a null name object. With a nonempty node name it returns immediately. The optional feature-log fallback for an empty name is a separate branch; this is not a material-title getter that automatically substitutes the default whenever `f378` is empty.

`moFeature_c::changeName` at `0x4bb3c560` calls `changeNameAndNotify` at `0x4bb3c690` with notification enabled, then updates common rename/comment state. Thus the title-setting operations below enter the actual inherited naming path, not an unrelated `f378` string assignment.

## Three independently observed static boundaries

### Constructor default

The material constructor initializes `f378` at `0x4beae33b`–`0x4beae348`, clears runtime `+0x384` at `0x4beae349`, sets folder state `f360=1`, then loads string ID `0x4497` at `0x4beae369`–`0x4beae373`. At `0x4beae384` it calls `changeName(this, loaded_string, null)`. Runtime `+0x380` is cleared separately at `0x4beae389`.

The native constructor therefore does not take an arbitrary user-supplied empty-folder caption. The research factory deliberately exposes caller `folder_names` and writes its selected value into the node name, a different construction choice from the native default. This is an authored override, not a captured value.

### Second serialization pass repairs an empty name only

Material-folder override `0x4beb1f10` first calls generic feature `SerializePass2` at `0x4bb39ab0`. On this concrete receiver the generic method's `+0x1248` dispatch resolves to the no-op leaf `0x4b27e120`.

The override then queries actual virtual `+0x88` at `0x4beb1f24`. Only when that returned CString has length zero does it load resource `0x4497` and call actual virtual `+0x90` at `0x4beb1f5d`, with null context. A nonempty name takes branch `0x4beb1f31` directly to the return.

Consequently this override alone does **not** explain replacement of the nonempty `authored material` input.

### Explicit material-folder title operation

The complete method at `0x4beb3fd0`, reached through this material folder's `+0x1ce0`, receives a separate owning concept/model and an incoming CString title. It queries the owner's `+0x200` collection branch. On the admitted branch it establishes the folder's position in that owner, then:

`title_to_apply = incoming_title if incoming_title is nonempty else resource(0x4497)`

The empty test is at `0x4beb4134`–`0x4beb413b`; the resource is loaded into the temporary title at `0x4beb413d`–`0x4beb4145`. After additional split-body visibility work, `0x4beb41c1`–`0x4beb41ce` invokes the actual material-folder `+0x90` name setter with that title and null context.

This bounded branch proves that a native operation can regenerate the persisted node name from material-title input independently of its old value. It does not read `f378` to produce that empty fallback. Its alternate owner-collection branch takes a different insertion path and must not be silently assigned the same rename behavior. The higher-level meaning of the owner `+0x200` predicate and the exact save/reopen caller were not fully recovered here.

## Material-field serialization distinction

`ResolvedFolders.py:38` serializes the inherited folder, then `f378` CString for versions greater than `0x109e`, and `flags380` u32 for versions at least `0x1423`.

Native serializer `0x4beb1d70` stores the material string separately at `0x4beb1daa`. Its current store branch packs the two runtime flags as:

`wire_flags = 0x80000000 | int(runtime_380 != 0) | (int(runtime_384 != 0) << 1)`

The packing instructions are `0x4beb1db0`–`0x4beb1dd8`. The load branch treats a word with bit 31 clear as the older Boolean encoding (`runtime_380 = int(word != 0)`, `runtime_384 = 0`), or uses bits zero and one when bit 31 is set (`0x4beb1e65`–`0x4beb1ea1`). The historical `b23e72c609caca0d0ca4acf871e9680a325f0548` factory emitted `flags380=0`. The three polygon candidates from `033b97679263fe31d7c4fb46899470be6c2923c5` were byte-identical and used that same legacy-false encoding. Native current storage of two constructor-false flags instead produces `0x80000000`. The updated shared factory now emits that operation-derived current-store word. This changes no name or caption and does not establish the cause of the measured name change.

The exported material-folder getter/setter pair `getMassPropOverridden` / `setMassPropOverridden` at `0x4b2852e0` / `0x4b291d30` reads/writes runtime `+0x380`. These addresses have other folded export aliases; their unrelated names do not change the concrete material receiver. The second runtime flag's semantic name is still unresolved here.
