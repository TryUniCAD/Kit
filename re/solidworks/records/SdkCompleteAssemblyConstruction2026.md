# Complete SDK ordinary assembly construction

The SDK constructs all twelve streams of an ordinary assembly from one actual
generated `PartCandidate`, two authored rigid occurrences and one aligned
coincident, parallel or positive driving distance mate. Eighteen complete
parent/child designs passed 396 exact typed stream round trips and independent
mathematical stream comparisons in 82 fresh guarded workers. Native acceptance
of this assembled SDK pair remains pending.

This is an internal construction API, with no public adapter write activation.
It admits one generated Front-supported plain rectangular forward blind-boss
definition, one independent active configuration and two direct proper rigid
placements. The generated child has an editable boss depth and no authored
sketch dimensions. Dimensioned rectangles, mixed child definitions, nested
definitions, unsupported mate kinds and saved model state are outside this
tranche. Ordered groups are a subsequent explicit extension.

## Actual graph ownership

`MakeAssembly` consumes the actual `PartCandidate`. It uses its original part
root, active configuration, registered principal planes, model header and
manager header directly. It never decodes a child file to obtain construction
state. Its own `moAssembly_c` is allocated as that concrete class, initialized
through the common model constructor, and receives assembly-owned subclass
fields. It never relabels a part object as an assembly.

The assembly retains distinct named system features, a real origin sketch,
an independently serialized configuration manager and the resolved mate group.
It allocates folders before the cabinet and principal planes while publishing
their documented resolved order. System features retain their constructor
pending-update bit; the initial root, configuration and resolved occurrences
apply their separately proved clear operation. Finished native solve statuses
are never copied into fresh graphs.

One child directory entry derives its shared identity from the generated
child. Its users count is two; its file save event and manager save event come
from their separate actual child owners. Config-0's external table is parent
self first and child second, giving the ordinary direct child slot 4.
Both occurrences retain that same directory object. Their external feature
backlinks retain each actual occurrence. Configuration states retain a
componentless first entry followed by occurrence states in reverse insertion
order, with separate contextual paths and shared containing-file handles.

Child-local bounds derive from the neutral rectangle vertices and forward
depth. Parent boxes transform the local corners and independent sphere, then
apply the native ordered sphere union and correction. Header `fc4`, model
`f1560` and configuration `f4b0` count the actual direct occurrences. The
assembly manager header folds the actual target geometry and transform stamps
through the admitted direct part graph.

Existing SDK mate factories receive actual child datum nodes and share the
parent persistent allocator. A driving dimension allocates before its mate.
Resolved wrappers use a separate assembly counter and retain their actual
ordered occurrence backlinks. Both headers receive only the root and actual
mate creation logs; there is no separate dimension creation log. The mate
group's wire children remain empty because MatesList owns the mate graph.

parent-owned handles expose matching header/body views, preserving pooling
within the parent without mutating the child. This adds no native wire word.

## Reproducible process proof

Run `CheckSdkAssembly.py --root CHECKOUT --output NEW_DIRECTORY` with optional
`--planar-proof` and `--distance-proof` pointing to the published generated
proofs. The checker freezes the full Python closure before generation,
persists and hashes exact stdin bytes, then starts separate build, typed
preparation and independent mathematical counterpart processes. Both emitted
containers preserve explicit stream order, independently of sorted JSON
object order.

The [sanitized receipt](../measurements/2026/SdkCompleteAssemblyConstruction01.json)
binds raw result SHA-256
`a69db2088711b7062d739b6d7f53de31af1122b460d21ca91c1802616e1656e1`
and the 4,706-file source closure
`4c516990a5987ea87801b6e8a4e231cbb7ae005f67d6d6a6bc3e885733adb8fd`.
The eighteen designs cover three mate kinds, all principal axes, two unrelated
plain children, translated and rotated placements, and both fixed anchors.
Every parent has twelve streams and every child ten. All streams and whole
containers match the independent mathematical composer under the same
declared generated stream order. Sixteen malformed cases publish no artifact
and preserve the generated child. Twelve previously published coincident,
parallel and distance bundle regressions remain byte-identical.

Black, Ruff, strict Mypy, Pyright and steering checks passed on the scoped source and
integration paths. Native execution, sealed inputs and CAD runtime reads were
not part of this proof. The prepared positive-distance fixture is a disclosed
authored design; its predicted trees and edit geometry are not native results.
All public write and native-acceptance flags remain false.
