## Three concepts with different owners

| Concept | Actual witnessed owner | What it establishes |
| --- | --- | --- |
| Document density preference | UI Definition `f1688` | A user preference, independently measured as 1000 kg/m³ in the ordinary default recipe |
| Physical part density | Part `f1420` → `moMaterial_c.f08` → `moDensityParameter_c.f58`; also part-configuration `fc50` | The assignment operation writes the selected physical density into the parameter and configuration |
| Assigned database and material identity | Selected configuration visual-properties receiver `f78`, material-properties receiver `f20`, its IdName CString `f20` | A database/material identifier carried alongside appearance properties |
| Body assignment | Actual atom ID and active-configuration association/visual records | Body material cannot be inferred from the part folder label or from the first material record |
| Effective unassigned body density | Native mass divided by native volume | The earlier ordinary default cases measured 1 kg/m³; this does not derive from the UI preference or mass-unit format |
| Material folder caption | `moMaterialFolder_c` node name and separate `f378` string | Presentation which may be regenerated by the application; not proof that physical material is assigned |

The filenames `MaterialFields.py` span rendering and archive owners. They are not evidence that physical assignment is already modeled. Conversely, appearance and assignment are not wholly separate graphs: the configuration's visual properties carry the actual assignment identity. Changing RGB does not, by itself, establish physical assignment.

The [custom mass-unit receipt](../measurements/2026/SdkCustomMassUnitsNative01.json) records four generated variants, eight generated native phases, two healthy controls and ten distinct processes. Every recorded mass/volume density is 1 kg/m³. It proves the bounded unit-format lifecycle, not assigned materials. [BindCustomDensityMut](../../../src/convert/adapters/solidworks/Archive/Construction/Units/BindCustomDensityMut.py) constructs the density **unit**, not the physical density value. [MakeMaterial](../../../src/convert/adapters/solidworks/Archive/Construction/Presentation/MakeMaterial.py) explicitly constructs fresh empty presentation without claiming an assigned physical material.

## Database and material identity

`moModel_c::getMaterialName` at `sldmodu 0x4c022be0` resolves the requested/current configuration, gets its visual properties via slot `0x1040`, then calls `moVisualProperties::getMatProps`, `uoMaterialProperties::getIdName` and `parseIDNameForMaterialInfo`.

The actual part/base configuration vtable slot resolves to `sldmodu 0x4b289be0`, a `+0x78` pointer getter. `sldmfcu 0x3c922000` validates the material-properties receiver at visual properties `+0x20`; `sldmfcu 0x3c7de630` returns the IdName CString at material properties `+0x20`.

The material application routine at `sldmatu 0x3c3c7a10` builds IdName using declared format vocabulary `%s|%s` or `%s|%s|%d` at `0x3c3c817e` / `0x3c3c8191`, then calls `setIdName` at `0x3c3c81c8`. The two strings are database, then material. The optional integer has its own native selection condition; it must not be invented from a feature, atom or list position.

The parser at `sldmfcu 0x3c850ea0` splits at pipe delimiters, extracts the database and material, and optionally parses the integer using `%d`. It initializes that integer to -1. Its missing-name resource branch and legacy comparison with declared `steel` vocabulary are separate cases. They do not authorize replacing missing material identity with a universal default or treating every arbitrary pipe-containing string as an ordinary material.

The current SDK material-properties record already retains its IdName CString. This task supplies semantic ownership, not a rule to fill every other appearance property from a saved material row. The existing [display archive record](MaterialDisplayArchive2026.md) remains independently scoped.

## Actual body and custom-property owners

`moAtom_c::getMaterialId` at `sldmodu 0x4bcf7900` follows atom `+0x138` → owning model `+0x258` → active configuration `+0xd78`, then calls `getMatIdFromAtomId` with the actual atom ID `+0x140`. The configuration lookup at `0x4bdd9270` consults `+0x430`, with additional `+0xb00` and parent-atom fallbacks. This is not yet a complete precedence model for multibody/configuration inheritance.

`moAtom_c::getFullMaterialName` at `0x4bcf5f20` uses the resolved material ID, walks the active configuration's visual-property records at `+0x420`, parses their IdName strings, and accepts a parsed integer matching that resolved ID. `getMaterialNode` at `0x4b2879f0` separately returns a **material folder** pointer at atom `+0x1a8`; the export's concrete return class rules out treating it as the physical `moMaterial_c` density object.

`moAtom_c::getDensityValue` at `0x4bcf5670` has two domains. IDs strictly below -9 go to `moConfigurationMgr_c::getCustomDefinedMatDensity`; IDs at least -9 go to a separate built-in lookup at `0x4bcfa380`. Neither branch proves a universal default physical density.

The manager custom-density lookup at `0x4b894790` indexes its `+0x600` keyed object map. A matching nonnull `moCustomDefinedMaterialProperty_c` returns **`+0x28`**, and a missing/null entry returns zero. That property class serializes `CString f08`, `f64 f10`, `f64 f18`, `i32 f20`, `f64 f28` at `0x4b88a910`. Its constructor at `0x4b881600` initializes the empty string, `0`, `1`, `0`, `0` respectively. Only `f28` is bound as density here; unrelated fields are not repurposed as density. No saved values supply these constructor facts.

The SDK already retains manager `n600` and key/object framing, but does not register this nonempty property class in the inspected ConfigSchemas. Therefore an assigned save which actually reaches this class has a concrete next schema boundary. Not every assigned material is assumed to use this ID domain or populate this map. The similarly named manager `f590` name maps, configuration `f600` user map and manager `f600` density-object map must remain distinct.

## API and external data boundary

The exact `sldappu` wrapper forwards `SetMaterialPropertyName2` at `0x456d8780` to its inner part interface's slot `0x4c0`; `GetMaterialPropertyName2` at `0x456d2900` forwards to slot `0x4b8`. These wrapper bodies prove the signature/forwarding boundary, not the complete inner validation rules. The assignment method has no documented Boolean success result: the native source observer must verify getter identity and independent mass response.

Official API semantics support the proposed oracle procedure:

- [IPartDoc setter](https://help.solidworks.com/2023/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.IPartDoc~SetMaterialPropertyName2.html) takes configuration, database and material name; the older official page is API context, while the exact 2026 wrapper is independently pinned above
- [IPartDoc getter](https://help.solidworks.com/2024/english/api/sldworksapi/solidworks.interop.sldworks~solidworks.interop.sldworks.ipartdoc~getmaterialpropertyname2.html) returns material name and database identity, with blank identity when no material is applied
- [IBody2 assignment](https://help.solidworks.com/2024/english/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.IBody2~SetMaterialProperty.html) is a separate operation with a status enum and a valid configured material database requirement
- [2026 material schema getter](https://help.solidworks.com/2026/English/api/sldworksapi/SolidWorks.Interop.sldworks~SolidWorks.Interop.sldworks.ISldWorks~GetMaterialSchemaPathName.html) exposes the installed schema path
- [2026 visual-property example](https://help.solidworks.com/2026/English/api/sldworksapi/Get_and_Set_Material_Visual_Properties_Example_VB.htm) separately controls material color, hatch and appearance behavior

The pinned `sldmatu` image contains `xmlParseDatabase` at `0x3c4045d0` and `xmlValidateDOC` at `0x3c4051d0`. Its schema getter at `0x3c3fa690` appends declared vocabulary `\xmlschema\sldmaterials.xsd` to the data directory. The dependency is therefore real at the assignment/API boundary. This does **not** prove that a saved assigned part requires an external database at every cold reopen.

There is also a material-specific storage observation: `iDumpMaterialStream` at `0x3c3e16a0` obtains current SolidStorage and looks up `swXmlContents` at `0x3c3e175d` and `MATERIALTREE` at `0x3c3e17cb`, then reads an archive and exports a diagnostic file. This proves an existing stored-data inspection path. Mandatory presence, native save construction, XML schema and cache-free absence behavior remain unmeasured. No opaque XML or captured database rows may be forwarded into a writer.

The host-only [recipe preparer](../../tooling/sw2026/materials/PrepareMaterialSourceRecipe.py) accepts that explicit metadata catalog, validates it and computes geometry, masses and ratios. It opens no CAD file and emits no CAD bytes. Catalog/API metadata is still missing, so this is not yet a runnable frozen native packet. Its synthetic host smoke data is clearly separate from actual installed material evidence.

The minimal lifecycle has ten fresh native processes: one fixed pristine control; for each design, initial native author/save, fresh reopen/material swap/save, fresh reopen/depth edit/save, and fresh read-only reopen; then the same pristine control. The initial author phase also performs a pure appearance contrast before physical assignment. A material swap must change mass by `rho_second / rho_first` while volume, area, center and intent remain fixed. The depth edit must keep material identity and effective density, retain the real origin anchor, and change volume/mass by `depth_edited / depth_original`. Every mass is independently predicted as `rho * width * height * depth` in SI units. The original, swapped and depth-edited states each receive a fresh-process reopen.

Record both part and actual-body material getters without presuming they match. A separate disposable body-assignment contrast can then bind inheritance/override/removal and the exact map domains. It is not silently included in the ordinary part-only writer scope. A later database-availability probe must use an isolated author-owned copy; never rename or remove an installed material database to test absence.

Before any material writer is written, root must lock independent original H sources/sidecars and preserve them unopened by the writer agent. Source-authoring tools and manifests must be committed before the native run. After disclosed qualification, inspect every material-bearing stream, correlate fields and exact typed round trips, and freeze the generative writer/equivalence method before hidden access. No current claim covers full material conversion, arbitrary assignments, mass overrides, body overrides, database-independent reopen or application acceptance.
