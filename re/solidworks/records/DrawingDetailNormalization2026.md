## Dimension-unit rules

For a nonnull actual user length unit and detail owner, the current-version branch at `0x4c23b24d` calls `moBaseDimDef_c::setLengthUnits` for exactly these dimension children:

`fe0`, `f2f8`, `f3f8`, `f500`, `f608`, `f830`, `f960`, `fa68`.

The setter `[0x3c7e6b70,0x3c7e6bfa)` destroys a different old unit, constructs an owned length unit and invokes its concrete copy slot `+0xc0`. The length vtable `0x3cc8b9d0` binds that slot to `0x3c914c40`. It copies the source format and unit code, including a separate dual copy when present. The fresh experiment admits only existing generated millimetre/degree formats with no incoming dual owner; it does not generalize this operation to arbitrary saved formats.

For file version at least `0xf69`, the unit pass then applies:

| Destination | Computed source |
| --- | --- |
| Each of the eight length `ff0.f0c` | `min(the same dimension.f80, 16)` |
| Each independently allocated length `ff0.fb8.f0c` | `min(the same dimension.f84, 16)` |
| Angle child `f1f0.ff8.f0c` | `min(f1f0.f80, 16)` |
| Chamfer child `f830.ff8.f0c` | `min(f830.f108, 16)` |
| Base child `fa68.ff8.f0c` | Precision retained from the actual copied document angle unit |

The dual rule uses `f84`, not the distinct tolerance places at `f8c`. This explains why the earlier ISO dual saves have precision three and ANSI dual saves have precision two even though both document tables use four. It is a computed copy/override sequence, not a saved-unit default.

`getDualUnit` `[0x3c915f50,0x3c916065)` allocates only when its real `fb8` is null. Its actual `IsMetric` virtual chooses inch for a metric primary and millimetre otherwise. [The shared constructor](../../../src/convert/adapters/solidworks/Archive/Construction/Units/MakeDualLength.py) models that allocation and its precision-two seed. The later dimension-style override above remains a separate operation. The experiment uses the shared constructor and assigns its independently derived per-style precision afterward.

The branch below `0xf69` has different precision ownership. It is recorded in the complete native body and is not promoted by the version-19000 experiment.

## Empty exclusion lists

The full detail constructor calls `iInitExclusionList` at `0x3c7d1a54`. The helper `[0x3c7db220,0x3c7db2f5)` inserts nine literal unit tokens and a localized string requested with resource id `0x7fbe`. The pinned English resource table contains `µm` for that id; the JSON records the exact resource range and hashes. Active resource-handle/language selection was not traced and is not generalized.

For ordinary version 19000, `Serialize` reads the declared count and clears the constructed list only when that count is positive. A zero count skips clearing and skips reading rows. Constructor names therefore survive the zero-count wire representation. The branch below `0x17ff` explicitly calls the initializer; that legacy branch is not the explanation for the current saves.

This corrects the earlier broad description of the helper as a preference fill. The observed zero-to-ten transition is supported by constructor plus current load behavior. It does not prove that the application overwrites every caller-authored nonempty set. The next requests declare positive lists before construction: one uses the bound English unit vocabulary, and the other uses unrelated authored strings. No row is silently added after a saved input is read. An authored truly empty native set remains unsupported rather than being mislabeled as preserved.
